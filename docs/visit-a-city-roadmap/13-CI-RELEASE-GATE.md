# CI ხარისხის კარიბჭე და ხელით რელიზი

სტატუსი: **დასრულდა**
დავალება: `FND-03`
განახლებულია: 2026-08-19

ეს დოკუმენტი აღწერს FND-03-ის ერთიან წესს. ერთი და იგივე შემოწმება მუშაობს
ლოკალურადაც და GitHub Actions-შიც; თვითონ შემოწმება საიტს არ აქვეყნებს.

## ერთი სრული ადგილობრივი შემოწმება

```bash
python scripts/run_quality_gate.py --output dist --report artifacts/quality-gate-summary.md
```

ბრძანება ამ თანმიმდევრობით ამოწმებს:

1. Python-სა და ზუსტად დაფიქსირებულ dependency-ებს;
2. source/build/deploy სტრუქტურას;
3. YAML-ს, სავალდებულო ველებსა და კონტენტის კავშირებს;
4. ყველა unit test-ს;
5. ყველა `static/**/*.js` ფაილის სინტაქსს Node.js-ით;
6. სრულ სტატიკურ build-ს;
7. ყველა გენერირებული HTML გვერდის ადგილობრივ `href/src` ბმულს.

პირველივე შეცდომაზე პროცესი ჩერდება, კონსოლში წერს ზუსტ ეტაპსა და მიზეზს და
`artifacts/quality-gate-summary.md`-ში ტოვებს მოკლე წარუმატებლობის ანგარიშს.
წარმატებისას `dist/` არის შემოწმებული საიტი, ხოლო ანგარიშში წერია გვერდების,
ფაილებისა და ზომის შეჯამება.

## CI ქცევა

- pull request და `main`-ზე ყოველი ცვლილება მხოლოდ `verify` ეტაპს უშვებს;
- წარმატებული შემოწმება 14 დღით ინახავს `dist/`-სა და მოკლე ანგარიშს;
- ჩვეულებრივი push production deploy-ს **არ** იწვევს;
- GitHub Pages deploy სრულდება მხოლოდ `Run workflow` → `deploy: true` არჩევით;
- `github-pages` environment-ზე სასურველია Required reviewers-ის ჩართვა.

## სხვა ჰოსტინგები

GitHub-ის workflow ვეღარ აქვეყნებს ავტომატურად, თუმცა Git-თან პირდაპირ
დაკავშირებულ Render/Netlify პროექტში ავტომატური deploy ცალკე dashboard setting-ია.
იქაც გამორთეთ Auto Deploy/Builds და რელიზის წინ ატვირთეთ მხოლოდ ხარისხის
კარიბჭით შემოწმებული commit. Repository-ში Render Blueprint-ს `autoDeploy: false`
აქვს. Netlify-ის UI-ში გამოიყენეთ **Stop builds** ან manual deploy policy.

## რელიზის მოკლე checklist

- ხარისხის კარიბჭე მწვანეა და artifact/report არსებობს;
- ცვლილება გადახედილია და კონტენტის გაფრთხილებები ცნობილია;
- მთავარ გვერდზე, რუკაზე, planner-ში, ავტოპარკსა და შესვლაში smoke test გაიარა;
- წინა წარმატებული artifact/commit ცნობილია rollback-ისთვის;
- მხოლოდ ამის შემდეგ ხდება ხელით deploy;
- deploy-ის შემდეგ მოწმდება მთავარი URL, რუკა, ავტორიზაცია და ერთი მარშრუტი.

Rollback-ის მიზეზებია ცარიელი გვერდი, გატეხილი რუკა/planner, ავტორიზაციის სრული
შეფერხება, დაკარგული კონტენტი ან ძირითადი მობილური flow-ის დაბლოკვა. ასეთ დროს
დაბრუნდით წინა წარმატებულ artifact/commit-ზე და პრობლემა ცალკე გაასწორეთ.
