# Static-first product hardening implementation plan

Branch: `harden-static-rental-funnel`  
Prepared: 2026-08-14  
Scope: local implementation and verification only; no production deployment or push.

## Confirmed findings

- The Python → static HTML → Decap CMS architecture remains viable and will be preserved.
- Draft/published/archived content handling, strict placeholder validation, dual GEL/USD prices, multilingual content and a shared Leaflet workspace already exist locally.
- The current car-detail booking UI writes Firebase booking records and therefore exceeds the requested phase-one architecture. It will be replaced/augmented by a static inquiry flow: WhatsApp plus Netlify-compatible form submission. No payment gateway, inventory lock or transactional booking backend will be introduced.
- A WhatsApp URL helper exists in `build.py`, but it is not yet a reusable, context-preserving inquiry component across the requested page types.
- Planner travel time still depends on point coefficients and haversine distance. It needs curated corridor overrides and conservative difficult-road fallback logic.
- Planner exports `CITY_NAME` from a small hard-coded mapping while accommodation comes from `places.yml`; the duplicated source can still produce overnight/hotel mismatches.
- `open_year_round` exists in attraction content/CMS but is not consistently carried into planner decisions.
- Required-car facts and available-car recommendations still use separate calculations. One strict rank must drive both.
- Rental pricing currently counts every itinerary day; Tbilisi walking-only days are not separated.
- Attraction hero markup still needs explicit LCP handling and dimensions; car images remain owner-supplied publication data.
- Site identity/contact values are CMS-managed and strict validation already flags placeholders, but the production dataset still contains placeholder contact/social values.
- Sitemap still assigns the build date to every URL.
- Language-specific OG fallbacks are referenced; all six outputs must be verified/generated.
- Firebase/local fallback exists. Disabled/local-only copy must explicitly describe device-only storage.
- Existing worktree changes belong to the ongoing product work and will be preserved.

## Implementation work

### Planner and routing

- `content/settings/road_legs.yml`: authoritative curated important-corridor distance/time/difficulty/season overrides.
- `build.py::planner_data`: export road-leg matrix, unified place/city data, year-round/seasonal fields and one car-requirement rank.
- `static/planner.js::leg/seasonOK/nearestTown/recommendCar/render`: consume authoritative sources; add >6h and stronger long-day warnings; winter uncertainty; strict vehicle floor; matching overnight/accommodation; optional no-car Tbilisi days and adjusted rental window/cost.
- Tests: winter mountain, Svaneti/Ushguli, Tbilisi walking day, paved Kakheti and mixed 4x4 fixtures.

### Static rental conversion

- Add a reusable compact inquiry component generated by `build.py` and a small `static/inquiry.js` enhancement.
- Fields: pickup/return locations and dates, time, requested car, name, phone/WhatsApp, optional email and notes.
- Generate localized `wa.me` messages from admin-managed WhatsApp only.
- Add a Netlify Forms-compatible fallback preserving page, car, route and planner context.
- Insert contextually on homepage, fleet, car, planner result, route, attraction and region pages without overwhelming informational pages.

### Admin/content model

- Expand `admin/config.yml` car, site identity, commercial terms, images and availability fields with numeric/type validation and help text.
- Keep immutable slug/status behavior and ensure only published cars feed pages, recommendations, sitemap and schema.
- Consolidate commercial terms in a settings source and remove new duplication.
- Add `ADMIN_SETUP.md` with non-developer GitHub OAuth/Decap workflow. No credentials or passwords will be committed.

### Trust, SEO and media

- Derive fleet count from published inventory where used; remove/avoid fake ratings and claims.
- Ensure hero images are eager/high-priority with dimensions and safe responsive markup; gallery remains lazy and tolerant of missing files.
- Provide safe OG fallback for all six languages.
- Use source modification dates (or explicit updated dates) for sitemap `lastmod`.
- Verify Car/Offer JSON-LD uses actual published/admin-managed values and no fabricated reviews.

### Accounts

- Keep Firebase optional and isolated from rental inquiry.
- When disabled, clearly say saved data remains only on this browser/device.
- When configured, retain authenticated trip sync.

### Verification and documentation

- Extend automated checks for placeholders, links/images, canonical/hreflang, sitemap, JSON-LD, OG assets, overflow and the planner/inquiry regressions above.
- Run JS syntax checks, unit tests, full generated-site build and strict build.
- Create `IMPLEMENTATION_REPORT.md` mapping completed fixes to `AUDIT.md`, admin capabilities, owner inputs, limitations, deployment steps and test results.

## Explicitly not changing

- No React/Next.js rewrite: it would discard the existing static SEO/content engine without solving the stated gap.
- No payment gateway, live inventory lock or transactional booking database: phase one ends in a contextual inquiry.
- No fabricated phone, email, business details, vehicle photos, prices, availability or reviews. Missing owner data remains a strict-build blocker.
- No forced Firebase dependency for public browsing or rental requests.
- No production deploy, DNS change or GitHub push during local implementation/testing.
